# Common Kafka Issues

| No. | Issue | Issue Example | Symptom | Solution |
|---|---|---|---|---|
| 1 | Partition Bottleneck (Throughput Limit) | `stamps-topic` has only `4` partitions, so only `4` booking processor instances can consume in parallel even when traffic grows to thousands of events per second | Low throughput, slow processing, overloaded consumers | Increase partition count, for example `stamps-topic -> 32 partitions`, and run `32` booking processor workers. Use `employeeId` as the partition key to preserve ordering per employee while distributing load. |
| 2 | Hot Partitions | A large company with `10,000` employees clocks in at `9:00 AM`, and hashing sends too many `employeeId` values to the same partition | Kafka lag grows on one partition; consumer CPU spikes while other partitions stay relatively idle | Use a better partition strategy such as `hash(employeeId)` or `hash(employeeId + date)`. Also increase partitions to distribute load better. |
| 3 | Consumer Lag | Producer rate is higher than consumer rate, for example stamp ingestion = `2000 events/sec` and booking processor = `800 events/sec`; Kafka lag can grow to `1M events` | Kafka buffers events and bookings appear delayed | Scale consumers horizontally by adding more booking processor instances, optimize booking logic, and use batch processing such as processing `100` events at once instead of one by one. |
| 4 | Ordering Constraints | `START_WORK` lands in partition `1` and `BREAK_START` lands in partition `2` for the same employee | The booking processor may see `BREAK_START` first and `START_WORK` later, which breaks business logic | Always use a partition key. In this system, use `employeeId` so all stamps for the same employee go to the same partition. |
| 5 | Duplicate Event Processing | A processor writes a booking but crashes before committing the offset, so Kafka sends the event again after restart | The same booking may be generated twice | Make processing idempotent. Use a unique constraint such as `(employeeId, startTime, endTime)` or store processed event IDs. Kafka exactly-once semantics can also help, but add complexity. |
| 6 | Large Message Problems | Messages larger than `1MB`; this is generally unlikely in the stamp system because stamp events are small | Slower network transfer, broker memory pressure, consumer slowdown | Keep Kafka events small. Store large data in a database and send only a reference in Kafka. |
| 7 | Broker Disk Bottleneck | Producers write extremely fast and saturate broker disks | High disk I/O and increased latency | Add more brokers, increase partitions, use SSD storage, and increase replication cluster size. |
| 8 | Retention and Storage Growth | High traffic with long retention, for example retaining stamp events for `7 days` using time-based or size-based retention | Kafka disks fill up, storage pressure increases, and the cluster may crash | Configure proper retention, archive data to long-term storage, and rely on the database for long-term storage when needed. This is one reason stamps are also stored in a Stamp DB. |
| 9 | Producer Failure / Event Loss | A stamp is written to the database, but Kafka publish fails, so the booking processor never receives the event | Missing events; downstream processing never happens for that stamp | Use the Transactional Outbox Pattern: write the stamp and outbox record in the same database transaction, then let a background service publish events to Kafka. This guarantees consistency. |
| 10 | Kafka Cluster Failure | Broker crash, network partition, disk corruption | Cluster loses availability; producers and consumers may fail to read or write messages | Use replication with `replication.factor=3` so each event is stored on three brokers. If one broker fails, another replica can become leader. |

## Common Kafka Operational Issues

| No. | Operational Issue | Description | Typical Cause | Monitoring / Mitigation |
|---|---|---|---|---|
| 1 | Consumer Lag Spikes | Lag increases suddenly and messages are processed later than expected | Slow downstream processing or temporary traffic bursts | Track consumer lag closely and scale consumers or optimize processing before backlog becomes critical. |
| 2 | Rebalancing Storms | Consumer groups rebalance too often, causing interruptions and instability | Frequent consumer group membership changes | Stabilize consumer instances, avoid unnecessary restarts, and tune consumer group settings to reduce rebalance frequency. |
| 3 | Disk Space Exhaustion | Kafka log storage grows faster than expected and brokers run out of disk | Retention settings are too large for the traffic volume | Monitor disk usage, tune retention, and expand broker/storage capacity before disks fill up. |
| 4 | ZooKeeper / Controller Issues | Cluster coordination issues affect partition leadership and broker management | ZooKeeper instability or controller problems, especially in older Kafka setups | Use strong broker and controller monitoring, and prefer newer Kafka architectures where applicable. |
| 5 | Monitoring Difficulties | Problems are discovered late because lag, disk, and broker health are not visible enough | Weak observability and missing alerts | Use monitoring tools such as Prometheus, Grafana, and Kafka Manager to detect lag and infrastructure issues early. |
